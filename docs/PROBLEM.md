# 문제 정의서

> 역할: 이 문서는 **왜** 만드는가에 답한다. 무엇을 만드는가는 `SPEC.md`, 상시 규칙은 `AGENTS.md`, 도메인 구조는 `ontology.yaml`이 정본이다.

## 1. 한 문장 문제

별도 QA 인력 없이 개발·디자인·기획을 겸하는 소규모 개발팀의 구성원이, 디자인-구현 차이 확인과 이슈 재현을 근거화하지 못해 **매 QA 라운드마다 같은 수작업(화면 대조, 이슈 재현, 테스트 데이터 세팅, 재확인)을 반복하며 시간을 잃는다.**

## 2. 대상과 비대상

- **1차 사용자**: 전담 QA 인력이 없어 개발자·디자이너·기획자가 QA를 겸하는 소규모 개발팀(3~10인 규모)의 구성원
- **비대상(현재)**:
  - 전담 QA 조직을 갖춘 대규모 엔터프라이즈 (별도 QA 프로세스·도구가 이미 있음)
  - 모바일 네이티브 앱 전용 QA (우리는 웹 화면 기준 Figma-구현 대조가 핵심)
  - 성능/부하 테스트 담당자

## 3. 증거

- 재현 정보 부족으로 재질문·재확인에 30분~하루가 소요됨 (로그1, 로그8)
- 색상/폰트/속성값 등 디자인-구현 불일치를 사람이 화면을 눈으로 대조하거나 캡처해 겹쳐보는 방식에 의존 (로그3, 로그7, 로그10)
- "이슈 확인 → 재현 → 수정 → 배포 → 재확인" 사이클이 매 PR·매 QA 라운드마다 반복되는 것이 가장 번거로운 작업으로 지목됨 (로그4, 로그6, 로그9)
- 테스트 데이터셋을 QA마다 직접 세팅해야 하고, 외부 서비스 의존성 때문에 데이터 불일치로 인한 오류까지 발생 (로그11, 로그14)
- 통합된 QA 도구의 부재로 각자 로컬에서 QA 체계를 구축하는 것이 조직 차원의 리소스 낭비라는 문제의식 (로그12)

## 4. 반증 조건

- **문제의 실재** (인터뷰 증거로 지금 판정)
  - 주장: 별도 QA 인력이 없는 소규모 개발팀 구성원은 디자인-구현 대조, 이슈 재현, 테스트 데이터 세팅 중 하나 이상을 QA에서 가장 번거로운 반복 수작업으로 겪는다.
  - 반증 조건: 대상 사용자 인터뷰 중 위 세 가지(대조/재현/데이터 세팅) 중 하나 이상을 QA에서 가장 번거로운 지점으로 꼽은 비율이 과반 미만이면 문제 정의 기각 — 지금까지 인터뷰 대상 4명 중 4명(100%)이 해당 사항을 언급함(로그1, 로그4, 로그6, 로그9, 로그11).
- **해결 가설** (제품 사용 관찰로 이후 판정)
  - 가설: Figma-구현 자동 대조와 재현 정보가 자동 포함된 구조화된 QA 이슈 생성이 QA 사이클의 반복 수작업을 줄인다.
  - 반증 조건: 자동 대조 결과와 구조화된 이슈를 받고도 사용자가 여전히 화면을 처음부터 수동으로 재대조하거나, 재현 정보를 추가로 다시 물어봐야 하는 경우가 관찰되면 가설 기각. 단, 자동 대조 결과 자체가 부정확해서 재확인하는 경우는 가설이 아니라 검출 정확도(SPEC.md AC1)의 문제로 별도로 집계한다.

## 5. 성공의 정의

- QA 세션당 "화면을 처음부터 다시 수동으로 대조"하는 횟수(활성화 지표) — 자동 Design Diff 결과를 그대로 채택하고 추가 수동 대조 없이 다음 단계(이슈 생성)로 넘어가는 비율로 측정
- 구조화된 QA 이슈 생성 후 재현 정보 부족으로 인한 추가 질문 발생 비율
- 재검증(Verification) 시 최초 등록된 재현 절차를 그대로 재사용하는 비율(리텐션 성격 지표) — 재현 절차를 다시 입력하지 않고 재검증까지 도달하는 이슈의 비율
