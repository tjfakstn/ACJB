# 문제 정의서

> 역할: 이 문서는 **왜** 만드는가에 답한다. 무엇을 만드는가는 `SPEC.md`, 도메인 구조는 `ontology.yaml`, 상시 규칙은 `AGENTS.md`가 정본이다.
> 증거의 로그·관찰 번호는 `docs/research/interviews.md`를 가리킨다.

## 1. 한 문장 문제

QA 전담 인력 없이 QA를 나눠 맡는 제품팀의 구성원이, 발견한 차이와 이슈를 **재현 가능한 근거와 함께 전달하고, 조치 여부를 바로 알고, 같은 절차로 다시 확인하지 못해**, QA 라운드마다 재질문·목록 확인·재현 절차 재입력의 왕복을 반복한다.

## 2. 대상과 비대상

- **1차 사용자**: QA 전담 인력 없이 QA를 나눠 맡는 제품팀의 개발자와 디자이너 — 응답자 중 9명 (로그 1, 2, 6, 7, 8, 9, 10, 11, 12)
  - 이슈를 받아서 고치는 쪽은 주로 개발자, 등록하는 쪽은 디자이너와 **기획자**다 — 기획자가 등록한 사례: 로그 2, 11, 12
- **비대상(현재)**:
  - 테스트 데이터 세팅·초기화가 주된 페인인 백엔드 QA — 온톨로지 범위 밖과 동일 (로그 4, 5)
- **검증 전 (근거가 부족해 대상·비대상을 아직 정하지 않음)**:
  - **기획자/PM** — 등록자로 자주 등장하지만 직접 응답이 없다. **후속 인터뷰 1순위.**
    - 판단 기준 *(후속 인터뷰 전 고정)*: 기획자/PM 3명 이상을 인터뷰해, 과반이 최근 QA에서 재질문·알림 누락·재확인 반복 중 하나 이상을 겪었으면 1차 사용자에 포함한다.
  - **QA 전담 담당자가 있는 조직** — 로그 5는 페인이 약했지만, 로그 3은 QA 담당자가 있는데도 디자인 차이 페인을 겪었다. 근거 2건이 엇갈려 판단을 보류한다.

## 3. 증거

- **재현 정보 부족 → 재질문과 대기**: "다시 답변을 듣고 다시 확인하기까지 30분정도", "이 과정에서 하루정도 걸렸습니다" — 재질문 한 번에 30분(로그 1), 2시간(로그 6), 하루(로그 2)가 걸린 사례가 있다 (로그 1, 2, 6, 9, 11)
- **등록·조치 알림 누락 → 목록을 직접 확인하고 따로 재촉**: "직접 이슈 목록을 확인해야 했습니다", "답답해서 슬랙으로 개인 디엠을 보냈음" (로그 2, 8, 11, 12, 관찰 1)
- **수정 후 재확인을 처음과 같은 과정으로 반복, 연결 화면을 놓침**: "처음 이슈를 확인했던 과정과 거의 똑같은 과정이었습니다", "종종 놓치는 경우가 있었음" (로그 1, 2, 6, 8, 9, 12, 관찰 1)
- **디자인-구현 차이를 사람이 눈으로 대조**: "개발자 모드에 들어가 정확한 색상 코드를 확인하고, 피그마에 들어가 … 비교함" (로그 1, 2, 3, 8, 10, 11, 관찰 1)
- **관찰**: 이슈 1건을 등록해 재확인하기까지 도구 간 창 전환 7회, 상태 수동 표기 건당 약 40초 (관찰 1)
- **반대 증거**
  - 대조: 로그 4, 9는 Figma-구현 차이가 AI·Figma MCP로 이미 줄었다고 답했다. 그래서 문제의 중심을 대조가 아니라 전달·확인 왕복에 둔다 (interviews.md B절 가설 검토).
  - 재현: 로그 4는 "요즘은 ai가 잘해줘서 시켜놓으면 5분안에 재현하는듯해요"라고 답했다. AI 도구를 쓰는 팀에서는 재현 정보 부족 페인이 약할 수 있다 → 4절 후속 검증에서 따로 센다.
- **증거의 한계**: 온라인 서면 응답 12건(개발자 8명 중 FE 5명으로 편중), 화면 공유 관찰 1건. 소요 시간은 응답자의 기억에 의존한 값이다.

## 4. 반증 조건

- **문제의 실재** (인터뷰 증거로 지금 판정)
  - 주장: QA를 나눠 맡는 팀의 구성원은 이슈 전달·조치 확인·재확인의 왕복을 **겪는다**.
  - 세는 방법: 실재는 "겪은 적이 있는가"를 묻는 주장이라 **전 문항**의 응답에서 센다. interviews.md의 대조 가설은 "시간의 대부분"이라는 **우선순위** 주장이라 "가장 번거로웠던 일"(Q3) 한 문항으로 셌다. 주장의 종류가 달라 세는 범위도 다르다.
  - 반증 조건 *(인터뷰 후 설정)*: 1차 사용자 9명 중 재질문·알림 누락·재확인 반복 중 하나 이상을 겪은 사례가 **3명 미만이면 기각** — 대상 또는 문제를 다시 쓴다.
  - 판정: **7/9명 → 기각되지 않음** (로그 1, 2, 6, 8, 9, 11, 12 / 항목별: 재질문 5, 알림 누락 4, 재확인 반복 6). 기준을 결과 뒤에 정했으므로 잠정 판정이다.
  - 분모: 주장의 대상이 "QA를 나눠 맡는 팀의 구성원"이므로 응답자 12명 전체가 아니라 1차 사용자 9명으로 센다. QA 담당자가 있는 팀(로그 3, 5)과 비대상(로그 4)은 제외했다. 참고로 12명 전체로 세어도 7/12명이다.
  - 후속 검증 *(아래 기준은 후속 인터뷰 전에 고정한다)*: 최근 QA 라운드 하나를 지정해 묻고, 다음 중 하나라도 해당하면 문제 정의를 다시 쓴다.
    - 응답자 과반이 그 라운드에서 재질문·알림 누락·재확인 반복을 한 번도 겪지 않았다
    - 응답자 과반이 전달·확인 왕복이 이미 도구(AI 재현, 자동 알림 등)로 해소되어 있다고 답한다 — 로그 4, 9의 반대 증거가 왕복에도 해당하는지 확인
- **해결 가설** (제품 사용 관찰로 이후 판정)
  - 가설: 이슈에 차이 값·화면·환경 정보와 재현 절차가 함께 기록되고, 상태가 "조치 완료"로 바뀌면 등록자에게 바로 알림이 가고, 재확인 때 그 재현 절차를 다시 입력하지 않고 불러와 쓸 수 있으면, 재질문·목록 확인·재입력의 왕복이 줄어든다.
  - 반증 조건: 관찰한 이슈의 **과반**에서 다음 중 하나가 나타나면 기각한다.
    - 기록된 정보를 받고도 담당자가 재현 정보를 다시 묻는다
    - 알림을 받고도 등록자가 목록·메일을 직접 뒤져 상태를 확인한다
    - 재확인 때 재현 절차를 다시 입력한다
  - 단, 기록된 값 자체가 틀려서 되묻는 경우는 가설이 아니라 기록 정확도(SPEC.md AC)의 문제로 따로 센다.

## 5. 성공의 정의

- **재질문 횟수**: 이슈 1건당 추가 정보 요청 횟수 (로그 1, 2, 6, 9, 11)
- **확인 지연**: 상태가 "조치 완료"로 바뀐 뒤 등록자가 재확인을 시작하기까지 걸린 시간 (로그 8, 관찰 1)
- **재입력 없는 종료**: 재현 절차를 다시 입력하지 않고 재확인까지 끝나 "해결 완료"된 이슈의 비율 (로그 1, 2)
- **리텐션**: 다음 QA 라운드에서도 계속 이슈를 이 방식으로 등록하는 팀의 비율
