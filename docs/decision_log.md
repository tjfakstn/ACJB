## 2026-09-09 브랜치 전략 개정: 영역별 브랜치 (main / dev / server / client)

- **결정**: 기존 `develop` + 이슈번호 기반 `feat/fix/...` 브랜치 방식을 폐기하고, `main`(절대 미작업) / `dev`(통합) / `server`(백엔드) / `client`(프론트엔드) 4개 브랜치 체계로 전환. `server`/`client` → `dev`는 셀프 머지 허용, `dev` → `main`은 배포 시점에만
- **왜**: 실제 개발 인력이 설만수 혼자인 비중이 커서, 이슈마다 브랜치를 새로 파고 리뷰어를 구하는 기존 방식이 오버헤드였음. 담당 영역(백/프론트)별로 브랜치를 나누고 `main`은 배포 게이트로만 쓰는 게 1인 개발 흐름에 더 맞음
- **결정자**: 설만수

## 2026-09-09 분야별 작업 흐름 구체화: 하위 분기 → 영역 브랜치 병합 → dev 통합

- **결정**: 백엔드 작업은 `server`에서 `server/<작업 설명>`으로 분기해서 진행 후 `server`로 병합, `server`가 어느 정도 쌓이면 `dev`로 통합. 프론트도 동일 패턴(`client/<작업 설명>` → `client` → `dev`)
- **왜**: `server`/`client`에 바로 커밋만 하면 작업 단위가 섞여서 되돌리기 어려움. 작업 단위별로 하위 브랜치를 나누되, 매번 `dev`까지 왕복하지 않고 영역 브랜치에서 먼저 모았다가 통합하는 게 1인 개발 흐름에 맞음
- **결정자**: 설만수

## 2026-09-09 브랜치 네이밍: feat/fix/docs 접두사는 유지, 영역 브랜치 하위로 이동

- **결정**: 기존 타입 접두사(`feat` `fix` `docs` `refactor` `chore`)는 폐기하지 않고 `server/feat-<설명>` `client/fix-<설명>`처럼 영역 브랜치 하위에서 계속 사용. `server`/`client` → 각 영역 브랜치로 머지 → 최종적으로 `dev`로 머지하는 3단계 흐름으로 확정
- **추가 규칙**: `docs/decision_log.md`, `docs/ssot.md`, `AGENTS.md`, `CONTRIBUTING.md`처럼 모든 브랜치에 공통 적용돼야 하는 문서는 `server`/`client`가 아니라 `dev`에서 직접 작업한다 (지금 이 항목도 `dev` 브랜치에서 작성 중)
- **왜**: 타입 접두사는 커밋 히스토리 가독성에 여전히 유용해서 유지. 공통 문서를 영역 브랜치에서 각각 건드리면 server/client가 서로 다른 버전을 갖게 되어 dev 통합 시 충돌 위험이 커짐 → 공통 문서의 단일 진행 지점을 dev로 고정
- **참고**: 이 규칙을 적용하면 `server`/`client`에 남아있는 문서 사본은 최신이 아닐 수 있음 — server/client → dev 병합 시점에 문서 충돌이 날 수 있으니, 필요하면 dev의 최신 문서를 server/client로도 가끔 가져올 것
- **결정자**: 설만수

## 2026-11-04 프로젝트 생성·초대, 2차 LLM·RAG, scan 혼합 방식

- **결정** (팀 회의):
  1. **프로젝트·멤버는 사용자가 앱에서 관리한다.** 10-28의 "프로젝트 멤버는 시드 데이터로 시작"을 뒤집는다 — CSV로 멤버와 프로젝트를 매핑하던 방식(`SeedLoader`, `data/seed/members*.csv`)은 폐기
     - 로그인한 사용자 누구나 프로젝트를 만들고, 만든 사람이 소유자(owner)가 된다 (AC16)
     - 프로젝트 멤버 누구나 구글 이메일로 초대한다. 서버가 그 이메일로 초대 메일을 보내고, 초대받은 사람이 **같은 구글 계정으로 로그인해 수락**하면 멤버가 된다. 초대는 7일 뒤 만료. 같은 이메일로 다시 초대하면 이전 대기 초대는 취소된다 (AC17·AC18)
     - 메일을 못 받아도 로그인하면 앱 안 초대함(`GET /invitations/mine`)에서 수락할 수 있다
     - 역할(designer/developer/planner)은 프로젝트별이고 수락할 때 본인이 고른다 — `role`을 `members`에서 `project_members`로 옮긴다
     - 멤버 제거는 소유자만. 제거된 멤버가 담당자인 미해결 이슈는 담당자를 비운다 (AC19)
     - 첫 로그인한 구글 계정은 그때 `Member`로 만든다
  2. **LLM은 프로젝트 초기 세팅에 쓰지 않는다.** 운영 중 2차 LLM 호출 지점을 두고, 그 지점에서 그 프로젝트의 이슈·스타일 차이·재검증 이력을 근거 문서로 검색(RAG)해 점검 후보를 제안한다. 결과는 근거 달린 제안일 뿐 자동 저장하지 않는다 (N16)
  3. **scan은 두 방식을 섞는다.** 프로젝트 초기에는 Figma 시안 전체와 배포된 웹 화면을 비교해 전체 QA 점검 사항·의심점을 제공하고, 이후에는 v1 문서의 단일 컴포넌트 scan(사람이 짝 지정, color·font_weight·radius)을 쓴다
     - 초기 전체 비교의 Figma 노드↔화면 요소 짝은 **LLM으로 추정**한다 — 결정 2의 예외로 허용(초기 전체 비교에 한함)
     - 비교 대상은 프론트 소스 코드가 아니라 **배포된 화면**(브라우저가 그린 값)이다 — 단일 컴포넌트 scan과 같은 값 추출 엔진을 쓴다
- **세부 결정**: 초대 메일은 팀 공용 Gmail 계정(SMTP, 앱 비밀번호는 `backend/.env`)으로 보낸다 — 초대한 사람 본인 Gmail로 보내려면 구글 앱 검수(gmail.send 권한)가 필요해서 제외. 초대 토큰은 SHA-256만 저장하고 원문은 메일 링크에만 둔다
- **왜**:
  - 1: 사용자가 생길 때마다 개발자가 CSV를 고치고 서버를 재시작하는 방식으로는 실제 서비스가 성립하지 않는다. 10-28에는 v1 범위를 줄이려고 뺐지만, 팀 바깥 사용자를 받을 수 없게 된다

## 2026-11-08 QA 흐름을 시안에 맞춘다: 담당 팀 배정 · 자동 Re-QA · 첫 QA 개발용 가짜 비교기

- **결정**
  1. **담당자 → 담당 팀**: 이슈의 `assigned_to`(멤버 id)를 `assigned_team`(`planner`·`designer`·`frontend`·`backend` — 프로젝트 역할과 같은 값, 화면 이름 기획팀·디자인팀·프론트엔드팀·백엔드팀)으로 바꾼다. 시안 ASN-01~04·QUE·ISS
     - 지정·변경은 프로젝트 멤버 누구나(정해진 4개 값이 아니면 400, null로 비우기는 400 — 지금과 같다)
     - 알림(AC3·AC11): 팀이 지정·변경되면(등록 때 포함) 그 프로젝트에서 **역할이 그 팀인 멤버 각각에게** `issue_created`를 정확히 1건씩, 재검증 `fail`이면 같은 멤버들에게 `recheck_failed`를 1건씩. 그 역할 멤버가 없으면 만들지 않는다. 같은 팀 재지정은 알림 없음(N5). `fixed` 알림은 지금처럼 등록자에게(AC4)
     - 권한(AC13): `in_progress`·`fixed` PATCH는 **역할이 그 이슈의 담당 팀인 멤버만**(팀이 없으면 누구도 불가). 소유자도 역할이 같아야 한다
     - 멤버 제거(AC19): 더 이상 이슈에서 지울 담당자가 없다 — 제거는 이슈를 바꾸지 않는다. 역할을 바꾸면 그 뒤로는 새 역할의 팀 권한·알림을 받는다(지난 알림은 그대로)
  2. **자동 Re-QA**(신규 AC28, 시안 RQA-01~03F·FIN): 소유자가 `POST /projects/{projectId}/re-qa`를 누르면 `fixed`이고 `source: first_qa`인 이슈들을 첫 QA와 같은 방법(같은 Figma 노드·코드 파일, 현재 브랜치 최신 커밋)으로 **다시 비교**한다(비동기 202, `GET .../re-qa`로 상태). 대상이 0건이면 409(`NOT_READY`), 첫 QA·Re-QA가 실행 중이어도 409
     - 같아졌으면 `Verification(result: pass)` → `resolved`, 여전히 다르면 `fail` → `needs_recheck` + 담당 팀 `recheck_failed` 알림. `verified_by`는 실행한 소유자, Verification에 `source: re_qa`와 다시 읽은 코드 값 `observed_value`를 남긴다(시안 RQA-03 "수정 전/후")
     - 근거를 다시 얻지 못한 이슈(노드·파일이 사라짐 등)는 바꾸지 않고 `fixed`로 두며 `skipped_count`에 센다. 실행이 실패하면 아무 이슈도 바꾸지 않는다(일부만 반영 금지)
     - 사람이 등록한 이슈(`source: manual`)는 지금처럼 등록자가 재현 절차로 직접 재검증한다(AC5·AC7 유지). 첫 QA 이슈도 수동 재검증은 그대로 가능하다
  3. **첫 QA 검증 범위**(시안 QA-01): `POST .../first-qa` body에 `scope`(1개 이상) — `size_spacing`(크기·간격·위치), `color_typography`(색상·타이포그래피), `border_radius`(테두리·모서리), `layout`(레이아웃), `presence`(UI 요소 존재 여부). 비면 400. property 범위 확정은 여전히 첫 QA 스파이크 뒤(N4) — scope는 실행에 기록하고 비교기가 따른다

## 2026-11-10 첫 QA 실제 비교기 — 방식과 검증 범위 확정

- **결정**:
  1. 스파이크(`docs/spikes/2026-11-10_first-qa-comparator.md`, 조건부 통과 — 정밀도 98.9%·주입 재현율 95%·안정성 98%) 방식으로 실제 비교기를 만든다. Figma 값은 노드 JSON에서 코드로 읽고, LLM(`claude-sonnet-5-5`)은 코드의 줄·토큰만 고르며, 값 변환·비교는 서버가 한다(N17)

  3. `StyleMismatch.property`에 `font_size`를 더한다 — 스파이크에서 범위·정확도가 가장 높았다
  4. 코드 입력에 테마 CSS(`@theme`)를 더한다. Tailwind 기본 테마는 서버에 둔다(Tailwind 4)
  5. 하위 요소 단위로 비교하므로 `StyleMismatch.node_id`는 매핑 노드 안의 요소 id(인스턴스 하위 id 포함)일 수 있다 — 프레임 미리보기(AC32)가 이 id를 받는다. 같은 코드 줄·property·값의 차이는 이슈 하나로 묶는다

## 2026-11-10 이슈 상세 코드 추적 — 문제 코드가 들어온 커밋·PR, 고친 커밋·PR

- **결정**: QA 이슈 상세(시안 ISS-02~04)의 "연결 코드 파일 · 컴포넌트"와 "GitHub 커밋 · PR"을 만든다(AC34). GitHub는 계속 **읽기만** 한다

## 2026-11-10 Re-QA에서도 검증 범위 선택 — 이전 범위는 다시 확인, 새 범위는 새로 비교

- **결정**: Re-QA 실행 화면에서도 검증 범위를 고른다(AC28). 지금까지 검사한 범위(첫 QA 범위 + 이전 Re-QA에서 더한 범위, `covered_scope`)는 항상 포함되고 잠겨 있어 빼지 못한다. 아직 검사하지 않은 범위를 더 고르면, 같은 실행에서 그 범위만 첫 QA와 같은 방식·근거 규칙(N17)으로 매핑 전체를 비교해 다른 항목을 새 이슈로 저장한다. 이전 범위는 지금처럼 `fixed` 이슈만 다시 판정한다
- **왜**: 첫 QA 때 고르지 않은 범위(예: 고정 문구)는 프로젝트가 끝날 때까지 검사할 방법이 없었다(설만수). 이전 범위를 다시 훑지 않는 것은 같은 차이가 이슈로 두 번 생기는 것을 막기 위해서다 — 미해결 이슈와 새 비교 결과를 맞춰 보는 규칙이 없어도 범위가 겹치지 않으면 중복이 생기지 않는다
- **세부**: 새 범위 비교는 Re-QA가 읽은 커밋(연결된 브랜치 최신)에서 한다 — 첫 QA 이후 고친 코드를 기준으로 봐야 이미 고친 차이가 다시 이슈가 되지 않는다. 새 이슈는 `source: first_qa`(이후 Re-QA 대상이 되도록), 이슈의 실행은 그 Re-QA(코드 추적의 커밋), 담당 팀 없음이라 알림 없음. 판정과 새 이슈는 한 트랜잭션이고 실패하면 범위도 더해지지 않는다. `fixed` 이슈가 없어도 새 범위가 있으면 실행할 수 있다. `scope`를 빼고 부르면 지금과 같다(기존 클라이언트·테스트 호환)
- **영향**: SPEC 4절·5절·AC28·N4·N16·N17, openapi v0.13.0(`re-qa` 요청 `scope`, `ProjectRun.added_scope`·`covered_scope`·`found_count`·`found_dropped_count`), db V15. 골든 케이스는 사람 승인 후
- **결정자**: 설만수. 자동 저장 지점이 늘어나는 범위 변경이라 오단비 확인 필요

## 2026-11-11 첫 QA가 Tailwind 밖의 스타일도 읽는다

- **결정**: 첫 QA·Re-QA의 코드 값 읽기를 Tailwind 클래스에서 **CSS 선언 한 개**까지 넓힌다 — 컴포넌트가 import한 CSS·SCSS·LESS·CSS modules 파일의 선언, styled-components·emotion 템플릿 줄, 인라인 `style`·CSS-in-JS 객체. 코드 묶음에 짝 파일과 import한 파일이 import하는 스타일시트를 넣는다
- **왜**: Tailwind를 쓰지 않는 프로젝트는 고정 문구 말고는 비교되는 값이 없었다. 동료평가 참가자가 자기 프로젝트를 연결할 때 막히는 지점이다(README 제한 사항)
- **근거 규칙(N17)**: LLM은 선언을 그 줄에서 그대로 베껴 올 뿐이고, 서버가 그 줄에 선언이 있는지 확인한 뒤 선언 글자만 보고 값을 읽는다. 저장소 CSS에 정의되지 않은 `var()`, 보간·SCSS 변수, em·%·`calc()`, 투명도 있는 색, 한 변만 적은 padding, 모서리마다 다른 반지름은 비교하지 않는다. 선언의 CSS 속성이 묻는 값과 다르면(배경을 물었는데 `color:`) 근거로 쓰지 않는다
- **확인**: 실제 LLM 1회 — CSS module·styled-components·인라인 style을 섞은 예제에서 넣어 둔 차이 3건을 모두 찾았고, 같은 값은 차이로 잡지 않았으며, 보간 값과 `@media` 줄은 고르지 않았다. 실제 프로젝트 정확도는 아직 재지 않았다. CSS 우선순위(같은 요소에 규칙이 여럿)는 LLM이 판단하지 못하면 건너뛰게 했을 뿐 서버가 계산하지는 않는다
- **영향**: SPEC 4절(첫 QA 비교 방식), README 5·6절. API·DB 변경 없음

## 2026-11-11 우리 서버 계정이 못 읽는 Figma 파일은 소유자 본인 토큰으로 읽는다

- **왜**: 다른 팀 파일(팀피셜)을 연결해 보니 Figma가 `429`, `Retry-After: 397192`(약 4.6일), `X-Figma-Plan-Tier: starter`, `X-Figma-Rate-Limit-Type: low`를 줬다 — Figma API 한도는 "파일이 있는 팀의 플랜 × 토큰 주인의 좌석"으로 정해져, 서버 계정이 속하지 않은 무료 플랜 파일은 몇 번만 불러도 며칠 막힌다. 비교 분석은 이 대기를 60초로 잘라 세 번 다시 시도하다 약 4분 뒤 실패했고(로컬 run 24, 운영에서도 두 번 실패 보고), 동료평가 참가자가 자기 파일을 쓰면 대부분 같은 벽에 막힌다. 사용자 토큰은 그 사람의 좌석으로 계산돼 자기 파일이면 정상 한도를 받는다
