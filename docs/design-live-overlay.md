# 설계안 — 사이트 위에 QAting을 얹는 실시간 QA(오버레이)

> 2026-11-24. 작성: 설만수(에이전트 초안). **결정됨(설만수)** — 4절은 1번만 바뀌어 연결 화면을 "핀 번호 보기 전용"으로 남기고, 2~4번은 추천대로(QAting 화면 안 등록은 캡처 위). 최종 결정은 `docs/decision_log.md` 2026-11-24. 오단비(범위)·최유정(화면 흐름) 확인 필요.
> 관련: SPEC AC29~AC31, `docs/decision_log.md` 2026-11-20(스니펫·연결 화면)·2026-11-24(연결 화면은 보기 전용).

## 0. 왜 바꾸나

지금 실시간 QA는 **QAting 화면 안에 배포 사이트를 넣는다**(iframe, 또는 `view.` 프록시). 이 구조에서는 로그인이 필요한 화면을 쓸 수 없다.

- 프록시: 도메인이 바뀌어 사이트의 로그인 쿠키가 따라오지 않는다.
- 원래 주소 iframe: 다른 사이트를 iframe에 넣으면 브라우저 기본값(SameSite=Lax)상 그 사이트 쿠키가 실리지 않고, 구글 로그인 화면은 iframe에 뜨는 것 자체를 막는다.

그래서 방향을 뒤집는다 — **배포 사이트를 원래 주소 그대로 새 탭에서 열고, 사이트에 넣은 스니펫이 그 위에 QAting 툴바를 얹는다.** 사용자는 평소처럼 로그인하고 실제 기능을 쓰면서, 문제가 보이는 요소를 골라 그 자리에서 등록한다(Marker.io·BugHerd·Jam과 같은 방식).

## 1. 화면 흐름

```
QAting 실시간 QA 화면
  [사이트에서 QA 시작]  ──(새 탭, 원래 주소)──>  배포 사이트 (로그인·기능 그대로)
                                                   └ 스니펫이 오른쪽 아래 QAting 툴바를 띄움
                                                        [핀 찍기] → 요소 고르기 → 작성 폼 → 등록
                                                        [이 화면 핀 n] → 기존 핀이 요소에 붙어 보임
  <──(등록 알림)──────────────────────────────────  등록 완료
  항목 목록·캡처 위 핀·상세
```

1. **시작**: QAting 실시간 QA 화면의 [사이트에서 QA 시작] → 배포 사이트를 새 탭으로 연다(`window.open`). 경로를 고르면 그 경로로.
2. **입장**: 새 탭의 스니펫이 QAting 탭과 인사하고 **오버레이 입장권**을 받는다(2절). 받은 뒤에만 툴바가 뜬다 — 일반 방문자에게는 아무것도 하지 않는다(지금 스니펫과 같은 원칙).
3. **핀 찍기**: 툴바 [핀 찍기] → 요소에 마우스를 올리면 강조, 클릭하면 고정(사이트의 클릭·제출은 막음 — 지금 `embed.js`의 고르기 코드 재사용). Esc로 취소.
4. **작성·등록**: 요소 옆에 작성 폼(제목·실제 결과·기대 결과·심각도·재현 절차 추가, Figma 프레임 선택은 경로↔프레임 연결이 있으면 자동). [등록]하면 증거 캡처(3절)와 함께 QAting에 저장 — `location_basis: live_element`.
5. **핀 보기**: 툴바 [이 화면 핀 n] → 지금 경로의 핀이 요소에 붙어 표시되고 스크롤·화면 변화를 따라간다(지금 `embed.js`의 위치 추적 재사용). 핀을 누르면 상태·제목·[QAting에서 보기].
6. **돌아가기**: 등록하면 QAting 탭의 목록이 바로 갱신된다(열어 준 탭에 `postMessage`, 탭이 닫혔으면 다음에 열 때 다시 읽음).

스니펫이 없는 사이트는 지금처럼 **서버 캡처·첨부 이미지 위에서 등록**한다(대체 수단 하나만 남김).

## 2. 인증 — 오버레이 입장권

QAting 로그인 쿠키는 배포 사이트에서 QAting API를 부를 때 실리지 않는다(다른 사이트 요청). 그래서 **짧게 쓰는 서명 입장권**을 따로 둔다.

| 항목 | 내용 |
|---|---|
| 담는 것 | 프로젝트 id, 멤버 id, 배포 출처(origin), 만료(4시간), 용도 `overlay` — 서버 비밀로 HMAC 서명(지금 `ProxyTokens`와 같은 방식) |
| 받는 사람 | 로그인한 그 프로젝트 멤버만(AC12) — `POST /projects/{projectId}/overlay-sessions` |
| 넘기는 법 | QAting 탭이 연 새 탭(`window.opener`)과 `postMessage`로 주고받는다. **주소에 담지 않는다**(기록·리퍼러에 남지 않게). 스니펫은 `event.origin`이 QAting 출처일 때만, QAting은 `event.origin`이 그 프로젝트 배포 출처일 때만 받는다 |
| 보관 | 스니펫이 그 탭의 `sessionStorage`에 둔다 — 탭 안 화면 이동·새로고침에도 유지, 탭을 닫으면 사라짐 |
| 쓰는 법 | `Authorization: Bearer <입장권>` 헤더. 쿠키를 쓰지 않으므로 CSRF 토큰이 필요 없다 |
| 검사 | 요청마다 서명·만료·용도 확인 + **`Origin` 헤더가 입장권의 배포 출처와 같은지** + **그 멤버가 아직 프로젝트 멤버인지**(DB). 하나라도 틀리면 401/403, 아무것도 바꾸지 않음 |
| 할 수 있는 것 | 아래 3개 엔드포인트뿐 — 이슈 상태 변경·삭제·멤버 관리 등은 입장권으로 못 한다 |

`window.opener`가 끊기는 사이트(응답 헤더 `Cross-Origin-Opener-Policy: same-origin`)는 QAting 화면에 "입장 코드 복사" 대체 경로를 둔다 — 사람이 새 탭 툴바에 붙여 넣는다. 이 경우만 입장권이 클립보드를 거친다.

## 3. 증거 캡처

로그인한 화면은 **서버(Playwright)가 다시 찍을 수 없다**(서버는 로그인 상태가 없다). 그래서 등록하는 사람의 브라우저에서 찍는다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **화면 공유 1장**(`getDisplayMedia`, 지금 탭 우선) — 추천 | 보이는 그대로(픽셀 정확) | 등록할 때 브라우저가 "이 탭 공유" 허락을 묻는다(탭당 한 번 허락해 두고 스트림을 유지하면 이후엔 묻지 않음) |
| DOM을 그림으로 다시 그리기(html-to-image 등) | 묻지 않음 | 외부 이미지·폰트·캔버스가 빠지거나 어긋날 수 있어 "증거"로 약하다 |
| 캡처 없이 등록 + 붙여넣기(Ctrl+V) 이미지 | 항상 가능 | 사람이 따로 찍어야 함 |

추천: **화면 공유 1장을 기본, 거절·미지원이면 붙여넣기/캡처 없이** — 핀 좌표는 요소 기준이라 캡처가 없어도 위치는 남는다. 캡처는 지금의 `captures/upload`와 같은 저장소(DB, 5MB)에 넣는다.

## 4. 정할 것

1. **연결 화면(프록시)** — (추천) **뺀다.** 로그인이 안 되는 화면을 기본값으로 두는 이유가 없어지고, `view.` 도메인·DNS·HTML 바꿔 쓰기·외부 사이트 중계라는 보안 표면이 통째로 사라진다. 남긴다면 "스니펫 없이 미리 보기(보기 전용)"로만.
2. **QAting 화면 안의 배포 화면(iframe)** — (추천) **뺀다.** 실시간 QA 화면은 항목 목록 + 캡처 위 핀 + [사이트에서 QA 시작]으로 단순하게. iframe에 넣을 때 생기던 문제(삽입 차단 헤더·쿠키·좌표 어긋남)가 같이 사라진다.
3. **증거 캡처** — (추천) 화면 공유 1장 기본 + 붙여넣기 대체(3절).
4. **지금 미커밋 작업본(`dev-feat-pin-capture`) 처리** — (추천) 요소 기반 핀(V19·V20, `PageElement`, `embed.js`의 고르기·추적, 서버 전체 페이지 캡처)은 살리고, 프록시(`liveqa/proxy/`, Caddy `view.`, `PROXY_*`, 골든 lp-001·lp-002)와 iframe 미리보기만 걷어낸 뒤 이 설계로 잇는다.

## 5. 바뀌는 것

**백엔드**
- `POST /projects/{projectId}/overlay-sessions` — 입장권 발급(세션 로그인, 멤버만). 응답: `token`, `expires_at`, `target_origin`, `open_url`
- `GET /overlay/context` — 입장권으로: 프로젝트 이름, 내 이름, 경로↔프레임 연결(작성 폼의 기준 프레임 자동 선택용)
- `GET /overlay/pins?path=` — 지금 경로의 핀(선택자·요소 안 비율·상태·제목) — 정렬 `created_at desc` 고정
- `POST /overlay/captures/upload` — 증거 이미지(5MB, png/jpeg)
- `POST /overlay/manual-qa` — 지금 `ManualQaRequest` 그대로, `location_basis`는 서버가 `live_element`로 고정. `screen_location`·`repro_steps`는 지금처럼 경로·요소에서 서버가 만든다(N1 — 지어내지 않음). 알림(`issue_created`)·`client_request_id` 중복 방지도 기존 그대로
- `/api/v1/overlay/**`만: 세션·CSRF 검사에서 빼고 `OverlayTokenFilter`가 인증, CORS는 **입장권의 배포 출처 하나만** 허용(쿠키 없음)
- 사용량 한도(AC36)는 기존 프로젝트 한도를 같이 쓴다

**스니펫(`frontend/public/embed.js`)**
- 지금 기능(요소 고르기·선택자·위치 추적) 유지 + 오버레이 모드 추가: 입장권 인사, 툴바, 작성 폼, 핀 표시, 등록
- 툴바·폼은 **Shadow DOM** 안에 그린다 — 사이트 CSS와 서로 섞이지 않게
- 크기 목표: 압축 전 30KB 이하, 외부 라이브러리 없음

**프론트(QAting)**
- 실시간 QA 화면: iframe·연결 화면 제거, [사이트에서 QA 시작]·입장 코드 복사·스니펫 설치 안내, 등록 알림 받으면 목록 갱신

**문서**: SPEC AC29~AC31 개정, openapi, decision_log, README 스니펫 안내(사이트 CSP에 `script-src`·`connect-src`로 QAting 주소 추가)

## 6. 보안 점검

| 위험 | 대응 |
|---|---|
| 사이트의 다른 스크립트가 입장권을 읽는다(같은 출처의 `sessionStorage`) | 팀 자기 사이트라는 전제 + 입장권 권한을 등록·조회 3개로 좁히고 4시간 만료. 이슈 상태 변경·삭제는 불가 |
| 다른 사이트가 입장권을 훔쳐 쓴다 | `Origin` 헤더 = 입장권의 배포 출처일 때만 받음, CORS도 그 출처만 |
| 멤버에서 빠진 사람이 남은 입장권으로 등록 | 요청마다 멤버 여부를 DB로 다시 확인 |
| `postMessage`로 엉뚱한 창에 입장권을 넘김 | 보낼 때 대상 출처를 배포 출처로 지정, 받을 때 `event.origin` 확인 |
| 툴바가 사이트 기능을 망가뜨림 | Shadow DOM, 고르는 동안에만 클릭 막기, 입장권 없으면 아무것도 안 함 |
| 입력값·쿠키 유출 | 스니펫은 요소 위치·선택자·글자 앞부분과 사람이 쓴 내용만 보낸다(지금 원칙 유지) |

## 7. 검증 — 작게 나눠서

| 단계 | 내용 | 완료 확인 |
|---|---|---|
| 1 | 입장권 발급·검사 + `/overlay/**` 4개 API | 백엔드 테스트: 위조·만료·용도 다름 401, 출처 다름 403, 비멤버·제거된 멤버 403, 등록 성공 시 `live_element`·필수 항목·알림 1건, 다른 프로젝트 데이터 접근 불가 |
| 2 | 스니펫 오버레이: 인사·툴바·고르기·작성·등록(캡처 없이) | 로컬 테스트 사이트(로그인 있는 화면 포함)에서 실제로 등록, QAting 목록 갱신 |
| 3 | 증거 캡처(화면 공유·붙여넣기) + 핀 보기 | 브라우저에서 캡처 저장·스크롤 따라가기 확인 |
| 4 | QAting 화면 정리(iframe·프록시 제거), 문서 | `./gradlew test`·`npm run build`, 골든 케이스(사람 승인) |

새 골든 케이스(사람 승인 필요): 입장권 401/403 경계, 출처 불일치 403, 입장권으로 상태 변경 불가, 오버레이 등록의 필수 항목(AC1)·알림(AC3).

## 8. 한계

- 팀이 사이트에 스크립트 한 줄을 넣어야 한다(스니펫이 없으면 캡처·이미지 등록만).
- 사이트 CSP가 외부 스크립트·요청을 막으면 CSP에 QAting 주소를 더해야 한다.
- 화면 공유 캡처는 데스크톱 크롬·엣지·파이어폭스 기준. 모바일 브라우저에서는 붙여넣기·캡처 없이로 대체.
- 앱(React Native·Flutter)은 대상 아님 — 지금처럼 위치 없는 수동 QA.
