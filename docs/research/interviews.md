# 인터뷰 프로토콜과 로그

## A. 인터뷰 프로토콜

- **방법**: 온라인 텍스트형 인터뷰. 서면 질문 특성상 관찰이 불가 → 응답자 대상 화상 후속 인터뷰(화면 공유 재현)로 보완 (관찰 1건, C절)
- **기간**: 2026-09-04 ~ 2026-09-23 (응답 12건)
- **대상(행동 조건)**: 최근 참여한 프로젝트에서 **QA를 직접 수행했거나, QA 이슈를 전달받아 수정해 본** 개발자·디자이너 등 IT 직군 종사자
  - 응답 12명: 개발자 8(FE 5, BE 2, 앱 1인 개발 1), 디자이너 4
  - 기획자/PM 응답 없음 — 한계
- **알아내려는 것(가설)**: QA 기간에 잃는 시간의 대부분은 수정 작업 자체가 아니라, **Figma 시안과 구현 화면을 대조하고 수정 후 다시 확인하는 반복 작업**에서 나온다.
  - 틀릴 조건 *(인터뷰 후 정리)*: Q3(가장 번거로웠던 일)에서 대조·재확인을 꼽은 응답이 과반(7명) 미만이면 기각
  - 인터뷰 전 원문: "IT직군 개발자들 및 종사자들은 QA과정에서 불필요한 시간 소모와 화면대조의 과정에서 비효율을 느낀다." → "느낀다"는 의견이라 반증할 수 없어 행동 기준으로 정리했다.

### Mom Test 자체 점검

- 강의02 실습 기준 "미래, 의견, 가정 유형 질문 0건"에 비춰 보면, **Q20이 가정형**이다 → 질문 표에서 제외하고, Q20 응답은 보조 근거로만 쓴다.
- 나머지는 과거 경험을 묻는 질문이다. 단, **Q3는 특정 사건을 지정하지 않은 일반형**("가장 번거로웠던 일")이라 A절 가설 판정 근거로는 한계가 있다 → 후속 인터뷰에서 "최근 QA 라운드"로 사건을 지정해 다시 확인한다.
- 한 사건을 따라가는 묶음: Q1 → Q2(한 프로젝트의 진행과 QA 방식), Q6 → Q7(한 디자인 차이 사례의 처리), Q9 → Q10 → Q11(한 이슈의 수신·원인 탐색·비용), Q15 → Q16(한 재확인 사례와 누락), Q21 → Q22(한 전달 사례와 그때의 기분)
- 서면 질문 특성상 한 사건을 끝까지 따라가는 후속 질문("그때 어떻게 했어요?")은 불가 → 후속 인터뷰로 보완.
- 우리가 조심할 유도 질문 (현재 문항에서 발견한 것):
  - ❌ Q6 "최근에 Figma 디자인과 실제 구현 결과가 달랐던 경험이 있었나요?" (우리 가설 쪽 주제를 먼저 꺼내고, 예/아니오로 답하게 함)
  - ✅ "최근 QA에서 수정 요청을 받은 화면 하나를 골라, 누가 어떻게 발견해서 어떻게 전달됐는지 순서대로 말씀해주세요." (주제를 정하지 않고 과거 사건을 따라감)
  - ❌ Q14 "최근 QA 과정에서 PM·디자이너·개발자 사이의 커뮤니케이션 때문에 일이 지연된 경험이 있나요?" (지연 원인을 커뮤니케이션으로 미리 정해 줌)
  - ✅ "최근 QA에서 이슈 하나가 등록부터 해결까지 며칠 걸렸고, 그동안 어떤 단계에서 기다렸나요?" (원인을 응답자가 말하게 함, 수치)

### 도출된 페인 (누적)

> 각 페인 끝의 → 는 `docs/ontology.yaml`에서 어디로 갔는지다. 범위 밖으로 뺀 페인도 지우지 않고 남긴다.

1. **디자인-구현 스타일 차이를 사람이 눈으로 찾아 대조** [문제] (로그 1, 2, 3, 8, 10, 11, 관찰 1)
   → `StyleMismatch`(expected_value, actual_value), `Screen` --implements--> `FigmaFrame`
2. **수정 후 재확인·회귀 확인을 사람이 반복** [문제] (로그 1, 2, 6, 8, 9, 12, 관찰 1)
   → `Verification`(result, scope). 자동 회귀 테스트는 범위 밖
3. **이슈 재현 정보 부족 → 재질문과 대기** [문제] (로그 1, 2, 6, 9, 11)
   → `QAIssue`(repro_steps, screenshots, screen_location), `IssueReportContext`
4. **디자인 변경사항(토큰·에셋·문구)이 공유되지 않아 반영 누락** [문제] (로그 1, 2, 10, 11, 12)
   → **범위 밖(v2 후보)** — 로그 11처럼 기존 우회로가 있음
5. **이슈 등록·조치 알림 누락, 상태를 손으로 관리** [문제] (로그 2, 8, 11, 12, 관찰 1)
   → `Notification`(event, channel), `QAIssue.status`, `QAIssue.status_history`
6. **기기·환경마다 다르게 보여 재현과 확인이 어려움** [제약] (로그 1, 6, 8, 9, 11, 12)
   → `Environment`(platform, device, browser, deploy_stage), `QAIssue.platform_scope`
7. **조건을 달성해야 보이는 화면에 진입하는 데 시간이 듦** [문제] (로그 8, 관찰 1)
   → `Screen.entry_condition`
8. **테스트 데이터 세팅·초기화 수작업** [문제] (로그 4, 5)
   → **범위 밖** — 이슈 전달·재확인 흐름과 별개
9. **자동화 도구를 시도했다가 유지비·학습비용으로 포기** [제약] (로그 1, 2, 5, 12)
   → 클래스 없음. Job Story의 Anxiety 근거, E2E 자동화를 범위 밖으로 둔 근거
10. **자체 우회로**: 캡처 겹쳐 비교(로그 2), 이모지로 상태 표기(로그 8, 관찰 1), 체크리스트+Playwright(로그 9), 토큰 동기화 파이프라인(로그 11) [우회로]
   → `QAIssue.status`·`status_history`(이모지 표기 대체), `StyleMismatch`(캡처 대조 대체)

## C. 워크플로 관찰 기록

> 서면 응답으로는 관찰이 불가능해 응답자 대상 **화상 후속 인터뷰(화면 공유 재현)**로 작성했다. 관찰 번호는 온톨로지 `evidence:`에서 로그 번호와 함께 쓴다.

**관찰 1** — 대상: 디자이너 C (로그 8의 응답자) / 일시: 2026-09-23(수) 20:00 / 방법: 화면 공유 재현 (약 10분)

- 재현 과제: "최근 QA에서 발견한 디자인 이슈 1건을 평소대로 등록하고, 개발자 조치 후 재확인해 상태를 바꾸는 과정까지 보여주세요." (개발자 조치 단계는 과거 Jira 티켓과 메일 기록을 열어 재현)

| 관찰 항목 | 관찰 내용 (본 것만 적는다) | 스펙 후보 |
|---|---|---|
| 단계와 도구 | ① 실기기(AOS)에서 배포 앱 실행 후 대상 화면 진입 → ② 이상 부분 캡처 → ③ 개발자 모드에서 적용된 색상 코드 확인 → ④ Figma에서 해당 화면 프레임을 검색해 색상 코드 대조 → ⑤ Jira 기능별 티켓 본문 표에 이슈 행 추가 (넘버링, 발생 화면, 해결책, Figma 링크, 공통/AOS/IOS 열) → ⑥ 티켓 댓글로 개발자 노티 → ⑦ 메일함에서 조치 완료 알림 확인 → ⑧ 배포 화면 재확인 → ⑨ 티켓 본문의 이슈 앞 상태 표기 수정 (사용 도구 6개: 실기기, 개발자 모드, Figma, 캡처, Jira, 메일) | 캡처한 화면에 대응하는 Figma 프레임 자동 연결, 이슈 등록 시 기기/OS 체크 필드(공통·AOS·iOS) 기본 제공 |
| 전환(Handoff) | 도구 간 전환: ①~⑤ 구간에서 앱↔개발자 모드↔Figma↔Jira 창 전환 7회. 사람 간 전환: ⑥에서 개발자에게 1회, ⑦에서 다시 본인에게 1회. ⑦에서 메일함을 2번 열었고, 그중 QA 관련 메일은 1건이었음 | 이슈 상태가 바뀌면 등록자·담당자에게 메일이 아닌 전용 알림 발송, 이슈별 스레드를 한 곳에 모음 |
| 우회로(Workaround) | Jira 상태 필드를 쓰지 않고, 본문 넘버링 앞에 "❗️확인 필요 / ✅해결완료 / 🚧재확인 필요 + 날짜·시간·이름"을 메모장에서 복사해 붙여넣고 날짜와 시간은 직접 타이핑함 (1건당 약 40초). 재현 중 "답이 늦으면 슬랙 DM으로 한 번 더 보낸다"며 과거 DM 화면을 보여줌 | 이슈 단위 4단계 상태(확인 필요 → 조치 완료 → 해결 완료 / 재확인 필요) 원클릭 변경, 조치 완료로 바뀌면 등록자에게 알림, 변경 시각·담당자 이력 자동 기록 |
| 멈칫(Hesitation) | ①: 조건을 달성해야 보이는 화면에 들어가려고 Figma 화면설계서를 다시 열어 진입 조건 확인 (약 1분 30초, 뒤로 가기 2회). ③~④: 옅은 그레이 비교 중 "기기 해상도 차이인가…" 발화 후 약 1분 멈춤, Figma에서 해당 레이어를 찾기까지 클릭 4회. ⑧: 여러 넘버링 중 해당 이슈 행을 찾기 위해 본문 스크롤 약 20초 | 이슈에 재현 경로·진입 조건 기록란과 딥링크 제공, 구현 화면과 Figma 값(색상·굵기) 자동 비교, 재확인 대기 이슈만 모아 보기 |

- 진술과 관찰의 차이:

## D. 핵심 Job Story

> 문장과 요소는 B절 로그 인용과 C절 관찰로만 구성했다. 사회적 Job은 근거가 1건뿐이라 후속 심층 질의로 보강한다.

> 배포된 화면에서 Figma와 다른 부분이나 버그를 발견해 이슈로 넘겨야 할 때, 나는 어느 화면의 어떤 값이 어떤 환경에서 다른지를 근거와 함께 한 번에 전달하고, 조치됐는지를 바로 알고 싶다. 그래서 되묻고 다시 대조하는 왕복 없이 재확인까지 끝낼 수 있도록. (로그 1, 2, 8, 11, 관찰 1)

| 요소 | 내용 | 근거 |
|---|---|---|
| 상황(트리거) | QA 기간에 배포 화면을 보다가 Figma와 다른 스타일이나 버그를 발견해 담당자에게 넘겨야 하는 시점 | 로그 2, 3, 8, 관찰 1 |
| 기능적 Job | 차이를 근거(Figma 기준값·실제 값·화면·기기)와 함께 이슈로 전달하고, 조치 후 재확인해 닫기 | 로그 1, 2, 8, 11, 관찰 1 |
| 감정적 Job | 디자인이 서비스를 망칠 수 있다는 우려, 답이 늦을 때의 답답함을 덜기 | 로그 3, 8 |
| 사회적 Job | 사소한 것까지 지적해 개발자를 귀찮게 하는 사람으로 보이지 않기 (심층 질의로 확인 필요) | 로그 10 |
| 현재 고용된 대안 | 캡처해서 Figma와 눈으로 대조, Jira·Notion·시트에 수동 등록, 이모지로 상태 표기, 메일·DM으로 재촉 | 로그 2, 8, 11, 관찰 1 |

**전환의 네 힘**
