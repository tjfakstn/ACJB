# 기술 타당성 스파이크 — Figma ↔ 코드 매핑(비교 분석, AC22)

> `SPEC.md` 4절이 "매핑 결과의 형태, 비교할 property 범위와 정확도 기준은 스파이크 후 이 절에 확정한다(N4)"로 남겨 둔 질문 중 **매핑** 부분을 판정한다. 비교할 property 범위(첫 QA, AC23)는 이 매핑이 통과한 뒤 별도 스파이크로 본다.

## 가장 위험한 가정

**가정**: 연결된 Figma **페이지**(섹션 안 프레임 포함)를 Figma REST API로 읽고, 연결된 GitHub 저장소·브랜치의 UI 코드를 GitHub API로 읽어 LLM(Claude) 한 번에 넘기면, LLM이 **화면 프레임 → 구현 파일**과 **화면 안 주요 노드 → 구현 컴포넌트**의 짝을 아래 성공 조건만큼 맞게 만든다. 구현이 아직 없는 프레임은 짝을 지어내지 않고 "없음"으로 둔다.

- 검증 대상: 이 저장소 자신 — Figma "UI Design - Refined" 페이지(`424:2`)의 섹션 "전체 서비스 최종 통합 UI"(`605:30464`)와 `tjfakstn/ACJB`의 `dev` 브랜치 `frontend/src`. 화면을 우리가 직접 구현해서 정답을 확실히 안다
- 범위 밖: 다른 저장소 구조(Next.js 라우팅, 모노레포 등), 수천 개 파일 규모, 앱(AOS/iOS) 코드. 결과를 그쪽으로 일반화하지 않는다

**실패 영향**: 매핑이 틀리면 첫 QA(AC23)가 엉뚱한 코드와 Figma 값을 비교한다. N17 검증(인용한 파일·줄에 값이 실제로 있는지)이 잘못된 이슈는 막아 주지만, 맞는 차이도 못 찾게 된다 — 첫 QA 자체가 의미를 잃는다. 실패하면 매핑을 사람이 지정하는 방식(단일 컴포넌트 scan처럼)으로 바꿔야 하고 시안 CON-06·WS-03 흐름이 달라진다.

## 시간 제한

**2시간 이내**. 판정할 수 없으면 "판단 보류"로 기록하고 AC22 구현을 시작하지 않는다.

## 입력과 방법 (실행 전 확정)

1. **Figma**: `GET /v1/files/{key}/nodes?ids={페이지 id}` 로 페이지를 읽고, 페이지 → `SECTION` → `FRAME`처럼 섹션 안까지 내려가 프레임을 모은다(지금 `/figma/sync`는 페이지 바로 아래만 읽어 섹션 안 프레임 0개가 된다). 프레임마다 이름, 자식 노드 이름(2단계까지), 텍스트 일부를 요약해 넘긴다
2. **GitHub**: `GET /repos/{repo}/git/trees/{branch}?recursive=1` 로 파일 목록을 받고 `frontend/src` 아래 `.tsx`·`.ts` 원문을 넘긴다(이 저장소는 약 18만 자라 그대로 넣는다 — 큰 저장소의 파일 고르기는 이번 범위 밖)
3. **LLM**: Claude `claude-opus-5-5`, 구조화 출력(JSON Schema)으로 프레임별 `{frame_id, file | null, nodes: [{node_id, file, symbol}]}`를 받는다
4. **검증**: 응답의 파일 경로가 트리에 없으면 버리고 센다(지어낸 경로). 프레임·노드 id가 입력에 없으면 버린다
5. 같은 입력으로 **2번** 실행해 결과가 흔들리는지 본다

### 발견 — 페이지에 지난 시안이 섞여 있으면 매핑이 같이 붙는다

연결한 페이지 "UI Design - Refined"에는 최종 섹션 말고도 지난 시안 섹션이 13개(프레임 256개) 더 있고, LLM은 그중 약 90개를 같은 파일에 매핑했다(예: `U01-01 랜딩 페이지 · 원본` → `LandingPage.tsx`, `Q-01 프로젝트 홈 — QA 실행 이력 없음` → `WorkspacePage.tsx`). 매핑 자체는 맞지만, 첫 QA가 이 짝들까지 비교하면 **지난 시안 값과 코드를 비교한 이슈**가 생긴다. AC22 구현 전에 정할 것:

- (가) 페이지 링크 대신 **섹션 링크**도 받는다(Figma에서 섹션을 골라 [링크 복사]하면 `node-id`가 섹션 id다)
- (나) 페이지는 그대로 받고, 비교 분석 결과에서 **소유자가 쓸 섹션을 고른다**
- (다) "최종 시안만 있는 페이지를 연결하세요" 안내만 하고 페이지 전체를 쓴다

### 결과를 읽을 때 주의할 점 — 쉬운 조건이었다

- 이 코드는 이 시안을 보고 만들었다. 시안 문구를 코드에 거의 그대로 옮겼고 컴포넌트 이름도 Figma 노드 이름을 따랐다(`Project Info` → `ProjectInfoCard`). LLM이 텍스트·이름으로 대조하기 가장 좋은 조건이다
- 시안과 구현 모양이 다른 곳(로그인, 초대 확인)에서 놓친 것을 보면, 문구가 다국어 파일로 빠져 있거나 시안과 다르게 구현된 저장소에서는 재현율이 떨어질 수 있다
- 그래서 판정은 "시안 문구를 코드에 쓰는 React 저장소(이 프로젝트)에서는 믿을 만하다"까지다. 다른 팀 저장소로 일반화하려면 조건이 다른 시험이 더 필요하다

- **놓친 이유 확인 — 요약 규칙을 바꿔 봤으나 채택하지 않음**: 프레임 요약은 자식 이름 8개와 앞에서부터 모은 텍스트 12개뿐이라, 멤버 관리 페이지 위에 다이얼로그가 얹힌 MEM-03·04 계열은 텍스트 12개가 배경 페이지 문구로 다 차서 다이얼로그 문구가 모델에 전혀 가지 않았다(MEM-03과 MEM-03C의 요약이 완전히 같다). 그래서 맨 위 레이어(다이얼로그)부터 텍스트를 모으고 16개로 늘려 같은 조건으로 2번 다시 쟀더니 재현율 81%·87%, 안정성 96%로 **나아지지 않았다**(MEM-05·MEM-03V·GST-03을 새로 놓침). 다이얼로그 문구가 보이자 모델이 "그 시점 코드에 이 상태가 없다"를 더 분명히 본 것으로 읽힌다 — `fa2e6fd`의 `InviteDialog`는 입력 한 단계뿐이고(초대 확인·처리 중·실패·이미 초대됨 상태 없음), `WorkspacePage`에도 "첫 QA 전체 통과" 상태가 없다. 놓친 것의 주된 원인은 요약이 아니라 **정답표가 "다이얼로그 파일이 있으면 그 상태 화면도 정답"으로 너그러운 것**이다. 요약 규칙은 원래대로 둔다
- 재현 자료: 입력 수집·채점 스크립트는 이번에도 커밋하지 않았다(scratchpad). 측정용 임시 테스트 러너와 요약 규칙 실험 코드도 지웠다

### 이 스파이크로 정하지 않은 것

- 큰 저장소에서 넘길 파일 고르기(이번엔 UI 코드 17만 자를 그대로 넣었다), 라우팅·스타일 방식이 다른 저장소
