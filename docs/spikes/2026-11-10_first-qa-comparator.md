# 기술 타당성 스파이크 — 첫 QA 비교기(AC23, N4·N17)

> `SPEC.md` 4절이 "비교할 property 범위와 정확도 기준은 스파이크 후 확정한다(N4)"로 남겨 둔 질문 중 **첫 QA의 값 비교** 부분을 판정한다. 매핑(비교 분석, AC22)은 `2026-11-07_design-code-mapping.md`에서 통과했다. 지금 운영에는 실제 비교기가 없고 개발용 가짜 비교기(`QA_FAKE_COMPARATOR`)만 있다.

## 가장 위험한 가정

**가정**: 비교 분석이 만든 **노드 ↔ 컴포넌트** 짝마다, Figma 노드 하위 요소의 스타일 값을 Figma API 노드 JSON에서 **코드로(결정적으로)** 읽고, LLM(Claude)은 컴포넌트 코드에서 그 요소를 그리는 **줄과 그 줄에 적힌 토큰**(Tailwind 클래스·문자열)만 찾게 한 뒤, 서버가 ① 그 토큰이 실제로 그 줄에 있는지 확인하고 ② 토큰을 저장소 CSS(`@theme`)와 Tailwind 기본 theme으로 **직접 값으로 바꿔** 비교하면, 아래 성공 조건만큼 맞는 차이를 찾고 틀린 차이는 만들지 않는다.

- 값을 LLM이 계산하지 않는다 — LLM이 고른 "줄·토큰"만 쓰고, 그 줄에 토큰이 없으면 버린다(N17: 코드 값은 인용한 파일·줄에 실제로 있을 때만)
- 검증 대상: 이 저장소 자신 — 운영 비교 분석 실행 15(프로젝트 26, `tjfakstn/ACJB` `dev` 커밋 `6ad7beb`, 섹션 "전체 서비스 최종 통합 UI")의 **노드 짝 10개 전부**. 화면을 우리가 구현해서 정답을 확인할 수 있다
- 범위 밖: Tailwind가 아닌 스타일(CSS 모듈·styled-components·인라인 style 객체), 반응형 변형(`md:`·`hover:`), 실제 렌더링 결과(브라우저 계산값 — 단일 컴포넌트 scan의 몫), 앱(AOS/iOS). 결과를 그쪽으로 일반화하지 않는다

**실패 영향**: 첫 QA가 틀린 이슈를 만들면 사람들이 자동 QA를 믿지 않는다(로그 8·11). 실패하면 첫 QA를 "LLM이 차이 후보를 제시 → 사람이 확인해 등록"으로 바꾸거나, 브라우저 계산값(scan) 기반으로 바꿔야 하고 시안 QA-01~04 흐름이 달라진다.

## 시간 제한

**3시간 이내**. 판정할 수 없으면 "판단 보류"로 기록하고 실제 비교기 구현을 시작하지 않는다.

## 입력과 방법 (실행 전 확정)

1. **Figma 사실값(결정적)**: 노드 하위 트리를 위→아래 깊이 우선으로 최대 40개 요소. 보이지 않는 요소와 벡터·선·도형은 뺀다. 요소마다
   - TEXT: `text`(문자), `color`(단색·불투명 fill), `font_weight`, `font_size`
   - 그 외: `background`(단색·불투명 fill), `radius`(네 모서리가 같을 때), `padding`(오토 레이아웃), `gap`(오토 레이아웃 itemSpacing), `border`(단색 stroke 색), `shadow`(있음 여부 — 이번에는 비교하지 않고 개수만 센다)
2. **코드**: 짝의 파일 + 그 파일이 직접 import하는 저장소 안 파일(1단계), 줄 번호를 붙여 넘긴다. 테마는 `frontend/src/index.css`의 `@theme`과 설치된 Tailwind 4의 `theme.css`
3. **LLM**: Claude `claude-sonnet-5-5`(비교 분석과 같은 모델), effort high, 구조화 출력. 요소마다 이름·종류·경로·문자를 보여 주되 **Figma 스타일 값은 보여 주지 않는다**(값에 맞는 줄을 골라 차이를 숨기는 것을 막는다). 요소·property마다 `{file, line, token}` 또는 생략(못 찾음·동적 값)
4. **검증(서버 몫)**: 파일이 입력에 없거나 줄이 범위 밖이거나 토큰이 그 줄에 없으면 버리고 "지어냄"으로 센다. 토큰을 값으로 못 바꾸면(투명도 있는 색, 변형 클래스뿐, 동적 값) "읽을 수 없음"으로 센다. 바꾼 값이 Figma 값과 다르면 차이 후보. 허용 오차: 색 채널 ±3(oklch→sRGB 반올림), 길이 0.5px, `rounded-full` ↔ Figma 반지름 100 이상은 같음
5. 같은 입력으로 **2번** 실행해 차이 후보가 흔들리는지 본다
6. **주입 실험**: 1회차에서 "같음"으로 확인된 짝 중 property별로 고르게 20개를 골라 코드 사본의 토큰을 다른 값으로 바꾸고(예: `rounded-xl`→`rounded-lg`, `font-bold`→`font-semibold`, `p-5`→`p-4`, 색 토큰 교체, 문구 한 글자) 같은 방법으로 다시 돌린다

## 정답 (실행 전 확정)

- **차이 후보의 정답 여부**: 후보마다 사람이 Figma 요소와 코드 줄을 직접 보고 판정한다 — "실제 차이"(그 요소를 그리는 줄이 맞고 값이 정말 다름) / "엉뚱한 짝"(다른 요소의 줄) / "변환 오류"(토큰→값 변환이 틀림)
- **주입 실험의 정답**: 바꾼 20개는 모두 차이여야 한다(재현율). 바꾸지 않은 짝이 새로 차이로 나오면 틀린 차이다

## 결과 (2026-11-10)

**판정: 조건부 통과** — 사전에 정한 비교 규칙(v1)으로는 정밀도 82.5%로 **실패**였다. 틀린 후보 10개 중 9개가 LLM이 아니라 서버의 값 비교 규칙 문제여서 결정적 규칙 3개를 보완(v2)했고, v2로는 모든 기준을 넘었다. 다만 v2는 1·2회차 결과를 보고 만든 규칙이라, **v2를 고친 뒤 처음 돌린 주입 실행**(새 LLM 응답)을 독립 확인으로 삼는다. 표본이 작아(노드 10개, 저장소 1개, Tailwind만) 다른 화면으로 한 번 더 확인하기 전에는 결과를 일반화하지 않는다.

## 결정 제안 (사람 확인 필요)

1. **비교기 방식**: 위 방식(Figma 값은 코드로 추출, LLM은 줄·토큰만, 값 변환·비교는 서버, v2 규칙)으로 실제 비교기를 구현한다. LLM 호출은 매핑된 노드마다 1번(노드 파일 + 직접 import 1단계)
2. **검증 범위(scope) ↔ property 확정**(N4) — 지금 표(`QaScope`)는 측정할 수 없는 것을 약속하고 있다
   - `size_spacing`(크기·간격·위치) → `spacing`(padding·gap)만. 크기·위치는 레이아웃 결과라 코드 토큰으로 비교할 수 없다 — 이름을 "간격·여백"으로 바꾸는 것을 제안
   - `color_typography` → `color`(글자·배경·테두리 색), `font_weight`, **font_size**. `font_size`는 지금 `StyleProperty`에 없다 — 추가 제안(스파이크에서 가장 범위가 넓고 정확했다). `font_family`는 전역 한 줄이라 요소 비교에서 뺀다
   - `border_radius` → `radius`. `shadow`는 "있음/없음"만 알 수 있어 이번에는 뺀다
   - `layout` → 비교할 property가 없다(지금은 `spacing`과 같은 값) — **삭제하거나 `size_spacing`에 합치는 것을 제안**
   - `presence`(UI 요소 존재 여부) → "요소가 없다"는 LLM이 못 찾은 것과 구별할 수 없어 근거가 없다(N17). 고정 문구 차이(`text`)만 남기고 이름을 "고정 문구"로 바꾸거나 삭제를 제안
3. **코드 입력**: 운영 `CodeSelector`는 `.tsx`·`.ts` 등만 넘기고 CSS를 빼는데, 비교기는 테마(`@theme`이 있는 CSS, `tailwind.config.*`)가 필요하다. Tailwind 기본 테마는 저장소의 Tailwind 버전에 맞는 값을 서버에 둔다
4. **범위 밖 유지**: Tailwind가 아닌 스타일, `hover:`·`md:` 변형, 렌더링 결과(scan의 몫)
5. **추가 확인**: 구현 뒤 다른 화면(예: 최신 `dev`의 실시간 QA·이슈 상세)으로 같은 절차를 한 번 더 돌려 정밀도 90%를 다시 확인한다
